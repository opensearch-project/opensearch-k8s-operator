# Security

Two reconcilers handle the opensearch-security plugin:

* **TLS reconciler** (`security.tls`): configures TLS for the transport and HTTP interfaces. The operator can generate a CA and certificates (`generate: true`) or use certificates supplied in secrets. Generated certificates are rotated automatically before they expire.
* **Securityconfig reconciler** (`security.config`): builds the securityconfig (users, roles, ...) and applies it to the cluster.

The security plugin is enabled only when TLS is enabled for the transport or the HTTP interface (`IsSecurityPluginEnabled`). Without TLS the security plugin is disabled: the operator does not configure the demo certificates or demo securityconfig, and the configuration reconciler writes `plugins.security.disabled: true` into `opensearch.yml`. The configuration reconciler only renders `opensearch.yml` when there is something to write (`additionalConfig`, `additionalVolumes`, `nodeAttributes` or operator settings). A cluster with no TLS and none of those gets no rendered file and no explicit `plugins.security.disabled` setting.

All keys and certificates generated by the operator are stored in Kubernetes secrets. For transport the operator generates either one certificate shared by all nodes or, with `perNode: true`, one certificate per node.

## CRD

Abridged; see the [CRD reference](crd.md) for all fields.

```yaml
spec:
  security:
    tls:
      transport:
        enabled: true               # Optional. Default: enabled when the transport block is present
        generate: true              # Generate a CA and certificates. If false, provide secret (and optionally caSecret)
        perNode: false              # Generate one certificate per node instead of one shared certificate
        rotateDaysBeforeExpiry: 30  # Renew generated certificates this many days before expiry, -1 disables
        duration: 8760h             # Validity of generated certificates
        enableHotReload: true       # Reload renewed certificates without a restart (OpenSearch >= 2.19.1, default true on 3.x)
        secret:                     # generate=false: secret with tls.crt, tls.key and ca.crt (per node: <pod>.crt/<pod>.key)
          name: opensearch-transport-certs
        caSecret:                   # Optional: CA in a separate secret (ca.crt). With generate=true, ca.crt+ca.key are used to sign
          name: opensearch-ca
        nodesDn: ["CN=node-*"]      # generate=false: DNs of the node certificates
      http:
        enabled: true
        generate: true
        customFQDN: opensearch.example.com  # Optional extra name for the generated HTTP certificate
        rotateDaysBeforeExpiry: 30
        secret:
          name: opensearch-http-certs
        caSecret:
          name: opensearch-ca
        adminDn: ["CN=admin"]       # generate=false: DNs of the admin certificate used by securityadmin.sh
    config:
      securityConfigSecret:         # Optional. Secret with config.yml, internal_users.yml, roles.yml, ...
        name: opensearch-securityconfig
      adminSecret:                  # Admin client certificate (tls.crt, tls.key, ca.crt). Required if HTTP certs are not generated
        name: opensearch-admin-cert
      adminCredentialsSecret:       # username/password the operator uses. Required with a custom securityconfig
        name: opensearch-admin-credentials
      operatorClientCert:           # Optional kubernetes.io/tls secret: authenticate the operator via mTLS instead of basic auth
        name: opensearch-operator-client-cert
      operatorClientServerName: opensearch.svc.cluster.local  # Optional SNI/ServerName override
      updateJob: {}                 # Resources, labels, tolerations, ... of the securityconfig update job
```

`security.tls.transport.adminDn` is deprecated; use `security.tls.http.adminDn` for OpenSearch >= 2.0.

## Relevant opensearch config

The TLS reconciler adds the following to `opensearch.yml` (values shown for generated, shared certificates):

```yaml
plugins.security.ssl.transport.pemcert_filepath: tls-transport/tls.crt # per node: tls-transport/${HOSTNAME}.crt
plugins.security.ssl.transport.pemkey_filepath: tls-transport/tls.key  # per node: tls-transport/${HOSTNAME}.key
plugins.security.ssl.transport.pemtrustedcas_filepath: tls-transport/ca.crt
plugins.security.ssl.transport.enforce_hostname_verification: false    # true for per-node certificates
plugins.security.nodes_dn: ["CN=my-cluster,OU=my-cluster"]
plugins.security.ssl.http.enabled: true                                # false when HTTP TLS is disabled
plugins.security.ssl.http.pemcert_filepath: tls-http/tls.crt
plugins.security.ssl.http.pemkey_filepath: tls-http/tls.key
plugins.security.ssl.http.pemtrustedcas_filepath: tls-http/ca.crt
plugins.security.authcz.admin_dn: ["CN=admin,OU=my-cluster"]           # only when securityadmin.sh can run
plugins.security.ssl.certificates_hot_reload.enabled: true             # only when hot reload is enabled
```

The securityconfig reconciler adds `plugins.security.allow_default_init_securityindex: true` in the default-init case described below.

## Certificate renewal

A generated certificate is regenerated when it is within `rotateDaysBeforeExpiry` days of expiry, and always when it is expired, cannot be parsed, or is no longer signed by the current CA. With hot reload enabled the nodes load the renewed certificates in place. Without hot reload the renewal changes the node pool config hash, so the pods are rolling-restarted (see [configuration](configuration.md)). The operator exports the remaining validity as the `opensearch_operator_cluster_tls_certificate_remaining_days` metric.

## Applying the securityconfig

The operator always builds a generated securityconfig secret: the user's `securityConfigSecret` if set, otherwise its bundled defaults, plus the admin credentials. Whether `securityadmin.sh` can apply it is a separate question (`CanRunSecurityAdmin`), because `securityadmin.sh` authenticates with the admin client certificate and therefore needs TLS on the port it connects to:

* OpenSearch >= 2.0: the HTTP port, so HTTP TLS must be enabled
* OpenSearch < 2.0: the transport port, so transport TLS is sufficient

This yields two paths for getting the securityconfig into the cluster:

| Situation | How the securityconfig is applied |
|---|---|
| `securityadmin.sh` can run | The operator runs the `<cluster-name>-securityconfig-update` job, which invokes `securityadmin.sh` with the admin client certificate. The job is rerun whenever the securityconfig changes. |
| Security plugin enabled but `securityadmin.sh` cannot run (HTTP TLS disabled on >= 2.0) | The operator sets `plugins.security.allow_default_init_securityindex: true`, mounts the generated securityconfig secret into the nodes, and lets the security plugin load it into the security index itself when the cluster first forms. No admin certificate and no update job are involved. |
| Security plugin disabled (no TLS at all) | Securityconfig reconciliation is skipped entirely. |

Consequences of the default-init path:

* The admin certificate is not generated or required, and the webhook does not demand an `adminSecret` or `http.tls.generate: true`.
* The securityconfig is only read at initial cluster formation. Later changes to the securityconfig secret are not applied automatically, because there is no update job to rerun.
* The `plugins.security.allow_default_init_securityindex` flag is added before any early return in the securityconfig reconciler, so the node configuration is deterministic from the first reconciliation and does not cause a rolling restart later.

## Security resources as CRDs

Users, roles, role mappings, tenants and action groups can also be managed as individual custom resources (`OpensearchUser`, `OpensearchRole`, `OpensearchUserRoleBinding`, `OpensearchTenant`, `OpensearchActionGroup`) that are reconciled against the security REST API. See [OpenSearch API resources](opensearch-rbac.md).
